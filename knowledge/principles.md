# 原則

## 根公理

**從拿到圖到分享出去，中間的每一步摩擦，都是產品要消滅的東西。**

TinyImg 存在的理由，是讓「我有一張圖 → 處理好 → 交出去」這件事幾乎沒有阻力。
功能、技術、流程的取捨，最後都回到同一個問題：這讓那段路變短了，還是變長了？

## 衍生原則

### 1. 圖片不離開使用者的裝置

- 推導自：根公理。上傳代表要等待，也代表使用者得先決定「我信不信任這個網站」。
  完全在本機處理，這兩種摩擦一起消失。
- 意義：不上傳、不追蹤、執行時不載入遠端程式碼。
- 如何應用：任何需要網路或需要第三方程式碼的設計，都要先證明沒有本機替代方案。
  具體規則見憲章 II。

### 2. 誠實比看起來成功重要

- 推導自：根公理。悄悄給出錯誤的結果，是延後發生的摩擦：使用者事後才發現檔案
  沒壓到目標，或貼上的是一串文字，只好回頭重做，代價比當下就說清楚更高。
- 意義：做不到就明說；錯誤訊息要讓人知道下一步該怎麼做；處理流程不能無限期卡住。
- 如何應用：每個「可能失敗」的路徑都要有使用者看得見的結果。具體規則見憲章 IV。

### 3. 工具出現在使用者所在的地方

- 推導自：根公理。切換到另一個網站、另一個 app 本身就是摩擦，所以工具要能在網頁、
  瀏覽器外掛（截圖、右鍵選單、側邊欄）、PWA 裡直接叫出來。
- 意義：同一份核心與編輯器，服務多個平台；平台專屬的只有「殼」。
- 如何應用：新功能先放進共用的 core 或 editor，不寫成某個平台專用。
  具體規則見憲章 III。

### 4. 一個變更做完了 = 測試先行，而且 CI 全綠

- 推導自：根公理。回歸 bug 是最差的摩擦：原本能用的流程突然不能用。
  舊版的缺陷（PNG 品質參數無效、Promise 永不 resolve）都是沒有測試擋住的結果。
- 意義：先寫一個會失敗的測試，再實作；PR 的 CI 全部通過，才算完成。
- 如何應用：/knowie-next 規劃時，測試任務要排在實作之前；/knowie-judge 檢查時，
  發現沒有對應測試的產品程式碼就提出來。具體規則見憲章 I 和「開發流程與品質關卡」。
