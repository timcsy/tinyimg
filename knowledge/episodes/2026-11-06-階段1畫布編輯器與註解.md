# 2026-11-06 階段 1：畫布編輯器與註解

> 完成日期：2026-11-06（vision 階段 1 的完成日期）

## 為什麼

vision 的兩條最短路徑，「標註後分享」和「壓縮後上傳」，都需要一個以畫布為中心、可以非破壞式編輯的介面。
階段 0 只完成了功能和舊版對等。

## 怎麼做（權衡過的選項）

- **切成兩個 spec**：002（編輯、畫布、快捷鍵）和 003（註解），每一份都能獨立交付（原則 V）。
- **不用畫布函式庫**：Konva 和 Fabric 的場景圖綁定 DOM，無法在 Worker 裡匯出；Fabric 約 90 KB。
  改成自建標準化的 EditState（裁切 → D4 變換 → 縮放），用屬性測試證明像素精確（`specs/002-editor-canvas/research.md` R1、R2）。
- **UI 框架中途從 Svelte 5 改成 React 19**：使用者的決定，理由是維護性（[history/005](../history/005-UI框架從Svelte5到React.md)）。
  因為 core 和 editor 不依賴 UI，只需要改寫元件，001 的 E2E 一個都沒改就全部通過。
  過程中出現一個把「React」寫成「Rust」的 commit，經使用者確認是筆誤後撤銷。
- **註解存在原圖座標**，匯出順序是：馬賽克（真的破壞像素）→ 向量註解 → applyEdit → 壓縮（`specs/003-annotations/research.md` R1、R2）。
- **效能**：預覽改由 worker 產生（只解碼一次）、worker 快取解碼結果、畫布分成兩層。
  Firefox 的門檻仍待使用者決定（[draft](../draft/2026-11-06-SC-003在Firefox與WebKit的預算.md)）。

## 用到的概念

原則 2（誠實：馬賽克必須真的破壞像素、編輯後絕不回傳原始檔）；原則 3（核心與介面分離，讓換框架的成本很低）；
原則 4（測試先行；屬性測試加上注入錯誤檢查）。
