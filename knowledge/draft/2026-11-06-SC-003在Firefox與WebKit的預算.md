# SC-003 在 Firefox 與 WebKit 的預算

> 怎麼冒出來的：002 實作時，畫布預覽讓 12MP 照片從放入到出現結果的時間，在 Firefox 和 WebKit 上超過 3 秒。

## 現況（本機 macOS，背景還有其他專案的程序在跑）

| 做法 | Chromium | Firefox | WebKit |
|---|---|---|---|
| 001（沒有預覽） | 2.06 秒 | 2.15 秒 | 2.43 秒 |
| 002 初版：主執行緒再解碼一次 | 2.01 | 4.90 | 3.23 |
| A：worker 依序產生預覽（目前採用） | 1.98–2.13 | 2.86–3.10 | 3.07–4.09 |
| B：預覽與壓縮並行 | 1.51 | 4.0–6.6 | 2.65 |
| C、D、E：bitmap 或 canvas 縮放的其他組合 | 1.9–2.2 | 4.4–7.3 | 2.6–3.9 |

結論：A 整體最好。Firefox 和 WebKit 卡在 3 秒邊緣，而且同一方案的差異可達 1 秒，量測受背景負載影響明顯。

## 後續：worker 快取解碼結果（已完成，2026-11-06）

draft 裡推薦的效能項目已經實作：同一個檔案再次壓縮時（例如每次編輯），worker 沿用快取的解碼結果。

| SC-007（編輯後到新結果） | 快取前 | 快取後 |
|---|---|---|
| Chromium | 2.46 秒 | 2.01 秒 |
| Firefox | 6.72 秒 | 4.16 秒 |
| WebKit | 3.51 秒 | 2.39 秒 |

注意：量測時機器的 load average 高達 40 到 83（有其他專案的程序在跑），所以數字只能當相對比較；
同一批測試在負載較低時，SC-003 曾經三個瀏覽器都低於 3 秒（1.40 / 2.42 / 2.11 秒）。
建議在機器空閒時，或第一次在 CI 上跑時再做最終驗收。

## 待決定

SC-003 的 3 秒是否也適用於 Firefox 和 WebKit？

- **推薦**：維持 3 秒的目標，但以 Chromium 做嚴格驗收；Firefox 和 WebKit 用 5 秒當回歸防線（目前的暫定做法）。
  另外開一個效能項目：worker 快取解碼結果（之後每次編輯就不必重新解碼），並延後預覽產生，預期可以把兩者拉回 3 秒內。
- 替代方案：三個瀏覽器都嚴格 3 秒。這樣現在的測試會不穩定，需要先完成上面的效能項目。

## 目前的暫定狀態

`apps/web/e2e/perf.spec.ts`：本機 Chromium 3 秒，Firefox、WebKit 5 秒；CI 一律 10 秒。
