# SC-003 在 Firefox 與 WebKit 的預算

> 怎麼冒出來的：002 實作時，畫布預覽讓 12MP 照片從放入到出現結果的時間，在 Firefox 和 WebKit 上超過 3 秒。

## 現況（本機 macOS，背景還有其他專案的程序在跑）

| 做法 | Chromium | Firefox | WebKit |
|---|---|---|---|
| 001（沒有預覽） | 2.06 秒 | 2.15 秒 | 2.43 秒 |
| 002 初版：主執行緒再解碼一次 | 2.01 | 4.90 | 3.23 |

結論：A 整體最好。Firefox 和 WebKit 卡在 3 秒邊緣，而且同一方案的差異可達 1 秒，量測受背景負載影響明顯。

## 待決定

Firefox（以及 WebKit）的效能門檻是否和 Chromium 相同？目前涉及 SC-003（12MP ≤ 3 秒）、SC-007（編輯後 ≤ 3 秒），以及 003 的 SC-006（拖曳 ≤ 50 ms）。

- **推薦**：維持 3 秒的目標，但以 Chromium 做嚴格驗收；Firefox 和 WebKit 用 5 秒當回歸防線（目前的暫定做法）。
  另外開一個效能項目：worker 快取解碼結果（之後每次編輯就不必重新解碼），並延後預覽產生，預期可以把兩者拉回 3 秒內。
- 替代方案：三個瀏覽器都嚴格 3 秒。這樣現在的測試會不穩定，需要先完成上面的效能項目。

## 再更新（2026-11-06 21:00 之後）：「負載造成」的推測不成立

- 完整 `npm run verify`（負載 29–70）：Chromium 旋轉後預覽一次 748ms（平常 3–5ms），Firefox 出結果 5.1 秒，都失敗。
- 只跑依序執行的 E2E 兩輪（負載 38–60）：Firefox 出結果 5.6 秒、6.7 秒，失敗；Chromium、WebKit 通過。
- 只跑效能測試兩輪（開始時負載 33–35）：Firefox 處理照片 6.5 秒、6.6 秒，拖曳最慢 240ms，失敗。
- 對照：同一天稍早，負載 59–92 時只跑效能測試，3 輪全部通過（2.3–4.0 秒）。

結論：Firefox 的數字在這台機器上 2.3–6.7 秒之間大幅變動，而且和 load average、測試順序都沒有一致的關係。
AI 先前把失敗歸因於負載，這個歸因不成立；真正的原因不知道（可能是 load average 沒反映的資源競爭，例如記憶體或 GPU）。

推薦（待你決定）：在 CI 的乾淨機器上量到 Firefox 的實際分佈後再定門檻；在那之前，本機的 Firefox 效能失敗不擋 commit，但要在 commit 訊息裡寫明。

## 拆解耗時（2026-11-06，暫時探針各跑 6 次，探針已刪除）

| 瀏覽器 | 第一次畫出預覽 | 出結果 | 輸出 |
|---|---|---|---|
| Firefox | 1.4–5.0 秒 | 5.3–14.7 秒 | 每次都是 1001.11 KB · 3745×2501 |
| Chromium | 0.8–1.9 秒 | 2.3–3.5 秒 | 每次都是 962.25 KB · 4240×2832 |

- 輸出每次都一樣，所以變動的只有執行速度，不是演算法走了不同的路。
- Firefox 多做一輪縮小：Chromium 縮一次就達標，Firefox 要縮兩次（3745 ≈ 4240 × 0.883）。
  推論：Firefox 的 JPEG 編碼器在同樣品質下產出的檔案比較大，所以多一整輪二分搜尋；這部分的額外工作是固定的。
- 速度跳動的直接證據：量測時 CPU 用量排前面的有別的專案在跑 Rust 建置（`cella`、`stdlib-cache`）。
  load average 反映不出這種競爭，所以先前拿 load average 去解釋才會對不上。
- 推薦（待你決定）：Firefox 的門檻等 CI 乾淨機器上的分佈出來再定。是否要改進 `nextScale` 讓 Firefox 少做一輪，
  屬於核心演算法的效能改進，可以另開一個 spec，目前不做。
