## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把圖片壓到目標大小，並誠實告知結果 (Priority: P1)

使用者放入一張圖片，設定目標大小（預設 1 MB），工具自動產生不超過目標大小、畫質盡可能高的結果。
如果無論如何都壓不到目標，工具會明確告知「無法達成」，並顯示目前能做到的最小大小，
而不是悄悄給出一個超過目標的檔案。

**Why this priority**: 這是產品存在的核心價值，也是舊版最大的缺陷：預設的 PNG 完全壓不下來，
而且失敗時不會提示（見 knowledge/experience.md 教訓 A、C）。沒有這一點，其他功能都沒有意義。

**Independent Test**: 用一組固定的測試圖片（照片、截圖、透明 PNG、超大圖）逐一壓縮，
檢查每個結果要嘛不超過目標大小，要嘛被明確標示為「無法達成」。

**Acceptance Scenarios**:

1. **Given** 一張 4 MB 的 JPEG 照片、目標 1 MB，**When** 使用者放入圖片，**Then** 得到不超過 1 MB 的結果，並標示「已達成」。
2. **Given** 一張 3 MB 的 PNG 螢幕截圖、目標 1 MB、格式為「自動」，**When** 使用者放入圖片，**Then** 得到不超過 1 MB 的結果（舊版在此情況會失敗）。
3. **Given** 目標大小設得極小（例如 50 KB），而圖片無法在合理畫質下達到，**When** 壓縮完成，**Then** 介面明確顯示「無法達成目標」與實際可達的最小大小，並仍可下載該結果。
4. **Given** 原圖本來就小於目標大小，**When** 壓縮完成，**Then** 結果不會比原圖更大；若重新編碼反而變大，則保留原圖並告知「原圖已符合目標」。
5. **Given** 一張有透明背景的 PNG、格式為「自動」，**When** 壓縮完成，**Then** 透明區域被保留，不會變成黑色。

### User Story 2 - 用熟悉的方式放入圖片，取得結果 (Priority: P2)

使用者可以用拖曳、選擇檔案或貼上（Ctrl/Cmd+V）放入圖片；調整品質上限、目標大小、輸出格式；
看到壓縮前後的大小、尺寸與節省比例；最後把結果複製到剪貼簿或下載。

**Why this priority**: 這是和舊版功能對等的部分，讓新版上線後不比舊版差。

**Independent Test**: 依序用三種放入方式各放一張圖，改變每個設定，確認結果會更新，
並且複製與下載都能拿到正確的圖片。

**Acceptance Scenarios**:

1. **Given** 開啟網頁，**When** 使用者拖曳、選擇檔案或貼上圖片，**Then** 三種方式都會開始處理並顯示結果。
2. **Given** 已有結果，**When** 使用者調整品質上限、目標大小或格式，**Then** 結果會自動重新計算，且畫面只顯示最後一次設定的結果。
3. **Given** 已有結果，**When** 使用者按下「複製」，**Then** 圖片被寫入剪貼簿；若瀏覽器不支援，會顯示明確訊息並建議改用下載，不會改為複製一串文字。
4. **Given** 已有結果，**When** 使用者按下「下載」，**Then** 下載的檔名為「原檔名_compressed.副檔名」，副檔名與實際格式相符。
5. **Given** 連續兩次選擇同一個檔案，**When** 第二次選擇，**Then** 仍會重新處理。

---

### User Story 3 - 每次變更自動驗證並發佈 (Priority: P3)

維護者提出變更時，系統自動檢查型別、程式風格、測試與建置；變更合併到主線後，
網頁版自動發佈到公開網址，不需要手動上傳任何檔案。

**Why this priority**: 這讓「完成 = 測試先行且 CI 全綠」（原則 4）可以被強制執行，
也取代舊版「只用 CDN、手動部署」的做法（knowledge/history/001）。對終端使用者沒有直接可見的價值，
所以排在後面，但它是之後所有階段的前提。

**Independent Test**: 開一個故意讓測試失敗的變更，確認無法通過檢查；
合併一個正常的變更，確認公開網址在幾分鐘內更新為新版本。

**Acceptance Scenarios**:

1. **Given** 一個讓任一測試失敗的變更請求，**When** 自動檢查執行，**Then** 檢查失敗，並指出哪一項失敗。
2. **Given** 一個全部通過的變更合併到主線，**When** 發佈流程完成，**Then** 公開網址顯示新版本。
3. **Given** 核心壓縮模組的測試覆蓋率低於 90%，**When** 自動檢查執行，**Then** 檢查失敗。

### Edge Cases

- 放入的檔案不是圖片，或是瀏覽器無法解碼的格式（例如 HEIC、損毀的檔案）：在 10 秒內顯示明確錯誤，進度不會卡住。
- 放入動態 GIF：只處理第一幀，並告知使用者動畫不會保留。
- 超大圖片（例如 8000×6000 以上）：仍能完成處理，或在超出可處理範圍時明確告知，不會讓頁面無回應。
- 處理中又放入另一張圖或改設定：舊的處理結果不會覆蓋新的結果。
- 目標大小欄位為空、為 0 或非數字：不開始處理，並提示有效範圍（50–10240 KB）。
- 輸出格式選 JPEG 但原圖有透明區域：透明區域以白色填滿，並提示使用者透明度已移除。
- 剪貼簿只接受 PNG：複製時轉成 PNG，並提示「貼上後的檔案大小可能與壓縮結果不同」。

## Requirements *(mandatory)*

### Functional Requirements

**壓縮核心**

- **FR-001**: 系統 MUST 在給定目標大小與品質上限時，產出不超過目標大小、且在此限制下畫質盡可能高的結果。
- **FR-002**: 當調整畫質無法達到目標時，系統 MUST 逐步縮小圖片尺寸再嘗試，直到達成或縮到最小可接受尺寸（最長邊 320 px）。
- **FR-003**: 對不支援畫質參數的格式（PNG），系統 MUST 使用能實際縮小檔案的方法（色彩量化、縮小尺寸），而不是重複相同的嘗試。
- **FR-004**: 每次壓縮的結果 MUST 明確標示為「已達成」、「原圖已符合目標」或「無法達成」，並附上實際大小、尺寸與所用格式。
- **FR-005**: 結果標示為「無法達成」時，系統 MUST 仍提供能做到的最小結果供使用者選擇下載或複製。
- **FR-006**: 系統 MUST 提供「自動」輸出格式並設為預設：原圖有透明區域時輸出保留透明度的格式，否則輸出照片類有損格式。使用者也可以手動選擇 JPEG、PNG 或 WebP。
- **FR-007**: 壓縮處理 MUST 不阻塞介面：處理期間使用者仍能操作頁面（捲動、改設定、取消）。
- **FR-008**: 任何處理步驟失敗或超過 30 秒未完成，系統 MUST 結束該次處理並顯示可行動的錯誤訊息。
- **FR-009**: 新的處理請求 MUST 取代進行中的請求；畫面上只會出現最新一次請求的結果。

**網頁介面**

- **FR-010**: 使用者 MUST 能用拖曳、選擇檔案、貼上三種方式放入圖片；拖曳區域本身可點擊，且可用鍵盤操作。
- **FR-011**: 使用者 MUST 能設定品質上限（10–100%，預設 80%）、目標大小（50–10240 KB，預設 1024 KB）與輸出格式（自動／JPEG／PNG／WebP）。
- **FR-012**: 系統 MUST 並列顯示原圖與結果的預覽，以及兩者的檔案大小、尺寸、節省比例與結果狀態（FR-004）。結果比原圖大時，顯示「增加 X%」而不是負數的節省比例。
- **FR-013**: 使用者 MUST 能把結果複製到剪貼簿；瀏覽器不支援時顯示明確訊息並建議下載，MUST NOT 改為複製文字。
- **FR-014**: 使用者 MUST 能下載結果，檔名為「原檔名_compressed.副檔名」，副檔名與實際格式一致。
- **FR-015**: 介面 MUST 支援淺色與暗色模式（跟隨系統設定），並在 360 px 寬的螢幕上可完整操作。
- **FR-016**: 圖片 MUST 只在使用者的裝置上處理；執行期間 MUST NOT 把圖片傳到任何伺服器，也 MUST NOT 載入遠端程式碼。

**驗證與發佈**

- **FR-017**: 每個變更請求 MUST 自動執行型別檢查、程式風格檢查、測試、建置與核心覆蓋率檢查（≥ 90%），任一失敗即標示為不可合併。
- **FR-018**: 變更合併到主線後，系統 MUST 自動建置並發佈網頁版到公開網址，不需要手動步驟。

### Key Entities

- **壓縮請求**：來源圖片、目標大小、品質上限、輸出格式；每個請求有唯一識別，用來判斷是否已被新請求取代。
- **壓縮結果**：狀態（已達成／原圖已符合目標／無法達成）、輸出圖片、實際大小、輸出尺寸、輸出格式、所用畫質、嘗試次數。
- **來源圖片資訊**：檔名、原始大小、原始尺寸、是否含透明區域、是否為動畫。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在固定測試圖片集上，100% 的結果要嘛不超過目標大小，要嘛被標示為「無法達成」；靜默超標的次數為 0。
- **SC-002**: 測試圖片集中的 PNG 螢幕截圖，在目標 1 MB、格式「自動」時，至少 90% 能達成目標（舊版為 0%）。
- **SC-003**: 一張 12 百萬像素以下的照片，在一般筆電上從放入到看到結果不超過 3 秒。
- **SC-004**: 處理任何測試圖片期間，頁面持續可操作，沒有超過 200 ms 的無回應時段。
- **SC-005**: 舊版的五項功能（拖曳、選檔、貼上、複製、下載）在新版全部可用，各有自動化端對端測試涵蓋。
- **SC-006**: 所有失敗情境（非圖片、無法解碼、逾時）都在 30 秒內顯示錯誤訊息；處理卡住不結束的次數為 0。
- **SC-007**: 變更合併到主線後 10 分鐘內，公開網址顯示新版本。
- **SC-008**: 首次載入所需的程式碼（壓縮後，不含按需載入的編碼器）不超過 200 KB。

## Assumptions

- 技術選型依憲章「技術與平台約束」：TypeScript strict、Vite、npm workspaces monorepo、GitHub Actions、GitHub Pages。這些屬於 plan 階段的細節，不在本規格展開。
- 公開網址暫定為 GitHub Pages 預設網址 `https://timcsy.github.io/tinyimg/`；自訂網域仍未決定（見 knowledge/vision.md「未決」）。
- 預設格式改為「自動」，取代舊版預設的 PNG。理由見 knowledge/experience.md 教訓 B：舊預設是為了剪貼簿相容性，卻讓壓縮失效；剪貼簿相容性改由複製那一步自行處理。
- 舊版固定把圖片縮到 1920×1080 以內；新版只在需要達成目標大小時才縮小尺寸（FR-002），不再無條件縮圖。
- 目標大小上限從舊版的 5120 KB 放寬到 10240 KB，下限維持 50 KB。
- 本階段的介面刻意保持最小，只求功能對等；畫布式介面、編輯與註解屬於階段 1。
- 範圍外：畫布編輯器、註解工具、瀏覽器外掛、PWA、批次處理。
- 舊版的 `index.html`、`script.js`、`styles.css` 在新版上線後移除；在此之前保留於 repo 根目錄作為對照。
