# 功能規格：編輯後重新壓縮，從上次的縮放比例開始

**分支**：`007-warm-resize` · **建立日期**：2026-11-06 · **狀態**：小功能，簡化流程（spec、plan、tasks 合在本檔）
**輸入**：Firefox 的 SC-007（12MP 旋轉後出新結果 ≤ 5 秒）在低負載時仍失敗（5.3 秒）。拆解後發現：每次編輯都從原尺寸重新壓縮，
而上一次已經證明原尺寸放不進目標，所以每次都白做好幾次大尺寸的編碼；Firefox 的編碼器產出較大，比 Chromium 多一輪
（見 `knowledge/draft/2026-11-06-SC-003在Firefox與WebKit的預算.md`）。

## 使用者故事

### US1：編輯大圖時，新結果出來得更快（P1）

使用者放入一張需要縮小才能達標的大圖，之後旋轉、翻轉或加註解。新的壓縮結果應該更快出來，因為 TinyImg 已經知道
大概要縮到多大。

**驗收情境**
1. 同一個檔案、同樣的設定，編輯後像素面積不變（旋轉、翻轉、註解）→ 直接從上一次結果的縮放比例開始，不再嘗試原尺寸。
2. 從該比例開始仍放不進目標 → 繼續縮小，結果仍保證不超過目標。
3. 目標大小、品質上限或格式改變，或者裁切讓面積改變 → 不沿用，從原尺寸開始。
4. 沒有編輯 → 不沿用（保留「原圖已符合目標」的判斷）。

## 功能需求

- **FR-001**：`compressToTarget` 新增選項 `startScale`：介於 0 與 1 之間時，從「最長邊 × startScale」開始；其他值一律忽略。
- **FR-002**：worker 記住最近一次「已達成」結果的縮放比例，鍵為（檔案、目標大小、品質上限、格式、編輯後的像素面積）。
- **FR-003**：不超標的保證不變（原則 2：誠實比看起來成功重要）。

## 取捨

沿用比例時，不會再回頭嘗試更大的尺寸。如果編輯讓圖片變得比較好壓（例如刪掉了註解），結果可能比最佳解略小一點。
畫質差異很小，換來每次編輯都能更快拿到結果，符合根公理「消滅摩擦」。
